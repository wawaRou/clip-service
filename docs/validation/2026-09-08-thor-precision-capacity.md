本机中文字体使用 `/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc`；

2026-09-08，对当前解码帧驱动实现进行实测。每路队列容量为 6，CLIP 为
`openai/clip-vit-base-patch16`，batch=1；权重来自本机 Hugging Face 缓存。
TF32 权重为 float32，FP16 权重为 float16。未修改服务实现、CPU/GPU 时钟或功耗配置。

硬件为 NVIDIA Thor，PyTorch 2.14.0+cu132、CUDA 13.2、OpenCV 4.14.0。
真实源为 `rtsp://192.168.3.245:8554/living_room_c225_sub`，720p H.264，约 25 FPS。
多路场景是多个独立读取器订阅同一条真实流，不是不同物理摄像头的现场测试。
OpenCV 软件解码、JPEG 历史采样 30 FPS、每路推理上限 30 FPS 均保留。
所有测量中的 CLIP 会话使用真实帧基准、阈值 -1，确保持续推理。

## 模型编码速度

每项预热 80 次，再测 3 轮，每轮至少 3 秒；FPS 取三轮中位数。
计时显式同步 CUDA。预处理测试循环使用同一批从真实流捕获的 30 张 BGR 帧。
vLLM 进程保持驻留，此部分没有生成请求。

| 范围 | TF32 FPS | FP16 FPS |
| --- | ---: | ---: |
| GPU 图像前向，输入已在 GPU，排除预处理与输出拷贝 | 287.88 | 358.43 |
| 完整 BGR 编码：颜色转换、预处理、GPU 前向、CPU 特征输出及归一化 | 109.37 | 121.77 |

FP16 的完整编码吞吐在本次测试中高约 11.3%，GPU 前向高约 24.5%。
这些数字不包含读流、JPEG 历史采样、调度和其他模型的并行生成，不能直接除以 25
作为实际摄像头容量。相同 30 张帧的 FP16/TF32 特征余弦相似度最低约 0.9999955，
这只是数值一致性检查，不代替视觉变化检测质量验收。

## vLLM 仅驻留时

各档预热 5 秒，测量 25 秒。下表是各路推理 FPS 的平均值，括号内是该档所有摄像头
合计丢弃的队列帧数。每路接收帧率均约 25 FPS，采样时未出现陈旧流或推理错误。

| 同时推理路数 | TF32 每路 FPS（丢帧） | FP16 每路 FPS（丢帧） |
| --- | ---: | ---: |
| 2 | 25.07（0） | 24.96（0） |
| 3 | 24.83（9） | 24.37（45） |
| 4 | 19.60（536） | 17.42（754） |
| 6 | 11.92（1957） | 11.60（2009） |

接收与完成计数均以窗口差值计算；窗口开始时可能还有预热阶段积压，故短时完成 FPS
可能略高于接收 FPS。两种精度顺序执行、时钟未锁定，单次整链路差异不能单独归因于
精度。当前实现中的解码、CPU 预处理、JPEG 采样和同步开销限制了整体吞吐。

## vLLM 持续生成时

保留现有 `nvidia/Qwen3.6-35B-A3B-NVFP4` 服务。按用户描述设置每次五张真实图片、
输出结构化 JSON，测试具体条件为：

- 同时一个请求，完成后立即发送下一次，模拟持续负载。
- 每次从正在运行的摄像头 JPEG ring 获取最新五帧，原始分辨率为 1280 x 720。
- `response_format=json_object`、`temperature=0`、`enable_thinking=false`。
- 输出上限 256 tokens；本次请求输入为 4468 tokens，测量窗口内输出约 133–224 tokens。
- 每档等待首个有效 JSON 响应，再预热 3 秒，测量 25 秒。
- 首次五图请求耗时约 67.97 秒，作为冷启动单独记录，不计入稳态结果。
- CLIP 延迟按健康接口采样；不是完整逐帧分布。VLM 延迟是请求至完整响应的耗时。

| CLIP 场景 | 每路 CLIP FPS | 所有路合计丢帧 | 最差一路 CLIP P95 延迟 (ms) | VLM 响应中位数 (s) |
| --- | ---: | ---: | ---: | ---: |
| CLIP 不推理，仅 VLM | 不适用 | 不适用 | 不适用 | 3.16 |
| TF32，1 路 | 24.98 | 0 | 82.65 | 3.73 |
| TF32，2 路 | 24.98 | 1 | 204.35 | 4.24 |
| TF32，3 路 | 19.47 | 414 | 261.83 | 4.09 |
| FP16，1 路 | 24.32 | 17 | 86.61 | 3.38 |
| FP16，2 路 | 24.99 | 0 | 143.51 | 3.70 |
| FP16，3 路 | 20.63 | 326 | 260.49 | 3.74 |

FP16 单路出现一次约 863.84 ms 的编码长延迟，接收至编码完成的最大延迟约 895.09 ms。
该档数据保留，不因其他档位表现更好而剔除；本次没有定位长延迟原因。
FP16 首次进入混跑时曾在预热阶段遭遇 RTSP 短暂断流，未产生有效测量；视频恢复后
重测该档，上表及原始 JSON 使用重测数据。有效测量窗口内各路无陈旧流采样或推理错误，
共 47 个完成的 VLM 请求均可解析为 JSON 对象，不代表进行了输出语义准确性评估。
图片和输出长度随真实画面变化，因此响应时长不是固定 token 数的严格性能对照。

## 内存与 GPU

以 `nvidia-smi` 计算进程占用口径，VLM 全程约 84567 MiB（82.58 GiB）；
CLIP 混跑进程 TF32 约 964 MiB，FP16 约 646 MiB。这不包含 CLIP 的全部 CPU 内存，
也不能把这些数值与系统内存占用相加当作独立内存池。

| 混跑场景 | GPU 利用率采样均值 | 系统 MemAvailable 最低 (GiB) |
| --- | ---: | ---: |
| TF32，1 路 | 85.5% | 19.88 |
| TF32，2 路 | 93.5% | 19.27 |
| TF32，3 路 | 92.8% | 18.73 |
| FP16，1 路 | 85.0% | 18.71 |
| FP16，2 路 | 89.7% | 18.31 |
| FP16，3 路 | 89.5% | 17.76 |

GPU 全局利用率采样峰值为 98%，不能按进程分摊。未发生内存不足；阶段顺序执行，
系统缓存和分配器状态未重置，MemAvailable 不用于直接比较精度的独立内存需求。

## 容量判断

在当前链路、720p、每路需要约 25 FPS、同时一个持续五图 JSON 请求的条件下，
可把 **2 路同时激活的摄像头**作为初步容量预算；3 路无法维持每路 25 FPS。
FP16 在模型编码、两路混跑延迟和进程 GPU 内存方面表现较好，但本次也捕获到长延迟，
两种精度都不能据短时测量保证长期零丢帧。

这里限制的是同时持续推理的路数，不是配置文件中允许接入的摄像头总数。
降低每路推理频率、仅少数 episode 同时激活或降低 VLM 请求频率，可改变容量；
更多相机、不同分辨率、多请求并发、开启思考或更长输出都需要另行验收。
本次没有测试 batch 推理或硬件解码，不代表 Thor 硬件的极限。
