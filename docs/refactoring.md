## 已确定的约束

- 项目仅供用户个人使用，优先保持简单；不为假设中的规模或扩展需求增加复杂度。
- 使用 uv 原生虚拟环境，不使用容器；平台组合沿用 platforms.md。
- 所有摄像头流均由 Frigate 统一接入，没有其他来源。
- 重构需要改善配置体验、检查现有功能缺陷，并考虑多摄像头。
- 保留外部 Agent Server 管理检测会话、指定基准图并决定是否调用 VLM 的职责。
- 使用独立 TOML，仅填写必要项和覆盖项，其余使用默认值；环境变量用于凭据和少量部署值。
- 保留普通 HTTP 请求与 SSE 通知的通信方式；尚未获得破坏旧接口兼容性的确认。
- 首期按单个 Frigate 实例，显式选择摄像头及转发流。
- 支持运行中增删改摄像头，提供全局默认值和每路覆盖。修改 TOML 后显式重载，无需重启服务；TOML 是唯一持久配置来源。先校验，再按差异应用；校验失败继续使用旧配置。
- 普通检测参数调整保留会话和已有候选，重置尚未确认的变化计时；切换视频流、禁用或删除摄像头结束该路会话并通知 Agent Server。未变化的摄像头继续运行。
- 摄像头数量不在代码中固定上限；三台仅是用户当前预计规模。目标是尽可能快、争取 1 秒内发出候选通知；算力不足时公平处理各路最新帧、跳过旧帧，允许实际检测频率下降，暴露每路频率与延迟。此时不保证 1 秒内通知。
- 允许调整持续变化确认时间与候选五帧时间范围。Thor、Orin、M2 Max 均需实测，当前没有吞吐或延迟承诺。
- 重启后恢复拉流和缓存，Agent Server 重新建立检测会话与基准。
- 回执超时后候选过期，保留原基准继续检测；重复回执可安全重试，迟到回执不得影响新候选。SSE 重连后查询当前未处理候选，不做历史事件重放。
- 单个服务进程加载一份 CLIP 模型；全局配置目标检测 FPS，各路默认继承相同值，允许按路覆盖。按各路目标周期调度最新帧，不以无节奏的轮询速度决定实际检测频率。

## 当前实现的事实

- 旧项目已有 cameras 列表；每路有独立的 CameraWorker、缓存、检测器、episode 和 pending 状态，共享 ClipEncoder。
- 配置类已有默认值，但示例 JSON 重复列出了大量默认参数；模型默认路径绑定个人机器。
- 当前摄像头只配置名称和 RTSP URL，检测参数为全局配置。
- 当前业务由外部系统开启 episode、设置 baseline；CLIP 产生 candidate，外部系统回执后继续检测。

依据：旧项目 clip_gate/config.py、service.py、model.py 和 config.example.json。现有行为不自动等同于新项目需求。

## 精简实施方案

实现范围收敛为单进程、共享一份模型、各路独立状态，以及按每路目标 FPS 调度的简单推理循环。继续使用本地候选文件和 HTTP/SSE；配置加载与重载集中处理，普通工程细节采用简单默认实现。

1. 迁移配置和启动入口：精简 TOML 示例、全局默认值、每路覆盖、校验与显式重载。
2. 迁移视频缓存和检测逻辑：独立相机状态、共享模型、按目标 FPS 公平调度、动态增删改，修复断流和重复推理问题。
3. 迁移并完善 HTTP/SSE 与候选存储：兼容已有调用，补齐超时、对账、回执竞态和重启规则。
4. 用旧测试及针对实际缺陷的回归测试验证功能，再在可用硬件上验证推理和延迟。确认时间、取帧窗口、回执期限等采用可配置默认值，不预先承诺未测性能。

## 目标检测 FPS 与共享模型

- 各路独立接收视频并维护缓存、基准及会话；共享模型只用于推理，不共享各路检测状态。
- 各路默认采用相同的全局目标 FPS；每路按目标周期安排检测，执行时取该路最新且未处理的有效帧。同一目标频率不要求各路在同一瞬间推理。
- 无活跃会话、无基准、等待回执或无有效新帧时不执行该路检测，不靠重复推理旧帧补足 FPS。
- 算力与输入帧率足够时，应维持各路配置的目标检测 FPS；未被覆盖的各路目标值相同。过载时公平调度并跳过过期任务，不积压旧帧，报告每路目标 FPS、实际 FPS 和处理延迟。
- 用户预计硬件可能支持总计 100 FPS，但尚未实测；这一数字不是已验证能力、每路目标值或配置默认值。容量验证需包含图像预处理、模型推理和结果处理，实际目标 FPS 保留余量后确定。
- 已按用户确认在本地发布六项任务，每项独立文件；[任务 03：多路摄像头共享模型并按目标 FPS 检测](../.scratch/clip-refactor/issues/03-target-fps-scheduling.md) 的验收覆盖相同目标 FPS、按路覆盖、跳过无效检测和过载后的实际频率。

## 当前通知机制与延迟约束

- Agent Server 通过普通 HTTP 请求开启/停止会话、设置基准图、取候选图片和发送回执。
- Agent Server 另发 GET /api/v1/events 并保持响应连接，CLIP 在该 HTTP 响应中通过 SSE 推送 candidate_change。SSE 与普通接口由同一个 HTTP 服务提供。
- SSE 承载候选元数据和图片地址；JPEG 通过普通 HTTP 获取。每个事件包含 camera 和 episode_id，单个订阅可接收所有摄像头事件。
- 旧实现先确认变化、冻结并存储五帧，再发通知；候选 pending 期间不再产生新候选，等待外部回执。
- 默认 stable_seconds=1.0，五帧目标为首次变化起点之后 0、0.25、0.5、0.75、1.0 秒。确认与收集时间重叠，不能简单相加，但也不能仅靠更快 GPU 实现从变化开始到通知严格少于 1 秒。
- 需要分别定义真实画面变化到通知的端到端延迟，以及帧进入 CLIP 后的处理延迟；不应把 VLM 耗时混入候选通知目标。

## 已发现的缺陷与设计空白

以下依据旧项目实现核查，尚未迁移或修复。

- 缺帧后可能永久无法凑齐候选五帧：detector.py:90 的取帧失败路径不重置最初变化时间；已有模拟断流复现。
- 候选过期后仍保持 pending：storage.py:145 删除记录，但未解除检测器等待状态；过期记录又无法经正常接口回执。
- 无新帧、未设置 baseline 或处于 pending 时仍可能编码：service.py:274 未检查条件等待的超时结果，也未在编码前完整检查资格。
- 回执与停止会话存在竞态：service.py:171 在耗时编码后未重新核验 pending 身份，内存状态与持久化状态分步修改。
- 读流未配置打开/读取超时；关闭线程等待结束后未核验退出。最新帧接口也未拒绝陈旧画面，见 service.py:225、130。
- 显式空 cameras 列表回退为示例摄像头，见 config.py:50；不应把空配置静默变成个人环境。
- 实施时落实已确认的 SSE 补取、重启、回执超时与公平调度规则；记录缓存资源与时间戳语义，避免把本机收帧时间误称为摄像头采集时间。

## Frigate 接入事实

- RTSP restream 地址为 rtsp://<host>:8554/<stream_name>；需要已配置相应 go2rtc.streams。仅在 Frigate 中配置摄像头不保证存在该转发流。
- 摄像头名与 go2rtc 流名可以不同，一台摄像头可以有多个流。
- RTSP 认证与 Frigate HTTP API 认证分别配置；显式选择转发流可以暂不引入 HTTP 自动发现。

来源：[Restream](https://docs.frigate.video/configuration/restream/)、[配置 go2rtc](https://docs.frigate.video/guides/configuring_go2rtc/)、[多流映射](https://docs.frigate.video/configuration/live/#setting-streams-for-live-ui)。
